What runs

So that nothing changes by surprise while it runs, weed says which build runs, since when, with which configuration, and whether a restart would change any of it. You can ask on the command line, in the log, in /status and /metrics, and in systemctl status.

The build

$ weed version
weed v1.2.0
commit   46a37813bc81d7a1b9a8b1e2a9e1f3c3e6c2a0d4 (2026-10-28T16:07:11Z)
go       go1.27.3 linux/amd64
build    go:2CX-x4_-THjPR2Dy4JCE/TtMef8lUxfkIJsGhiXwh/3-NbDYhNvYZpdojQpjfp/Dg3...

The version is a release tag, or v0.0.0-<time>-<commit> for other commits, with +dirty (and "with uncommitted changes") if the tree had changes. A binary built without version control information (outside a git checkout, or with -buildvcs=false) says "(devel)". The build is the Go build ID, which the linker derives from the binary's content: two binaries with the same build are the same.

At startup

weed logs a "starting weed" record with its version, commit, build, pid and executable, and a "configuration" record with the configuration file, the SHA-256 of its content, and the value of every option, defaults included. Secrets that are set are shown as <redacted>.

level=INFO msg="starting weed" version=v1.2.0 commit=46a37813bc81d7a1b9a8b1e2a9e1f3c3e6c2a0d4 commit_time=2026-10-28T16:07:11Z modified=false build=go:2CX-x4_-THjPR2Dy4JCE/... go=go1.27.3 platform=linux/amd64 pid=4242 executable=/usr/local/bin/weed dir=/data tls=true authentication=x509,tokens,macaroons tpc=true reload_interval=1h0m0s
level=INFO msg=configuration file=/etc/weed/weed.toml sha256=b78bbdeed036... config.server.address="" config.server.port=443 config.server.dir=/data ... config.macaroons.secret_key=<redacted> ...

sha256sum /etc/weed/weed.toml tells whether the file is still the one weed runs with.

Restart pending

weed reads the configuration file only at startup, and a new binary only runs once weed restarts. So weed looks at both every minute, on reloads, and whenever /metrics or /status is read:

  • If the file now sets other values, weed logs a warning that names them.
  • If weed would not start with the file (a syntax error, an unknown option, a file that is gone), it logs an error: now, rather than at the next restart.
  • If the binary has been replaced by another build, weed logs the new one's version, which it reads from the file without running it.

 

level=WARN msg="restart pending: the configuration file has changed: server.port, tpc.enabled" reason=config
level=ERROR msg="restart pending: the configuration file has changed, and weed would not start with it: ..." reason=config
level=WARN msg="restart pending: weed's executable /usr/local/bin/weed is now v1.3.0 (commit 9c1e0a2b77d4 of ...) go1.27.3 linux/amd64, build go:..." reason=binary

Each is logged once, and "restart no longer pending" once the change is undone. Changes to comments and layout only are not reported. The status line of systemd says it too:

$ systemctl status weed
...
     Status: "Serving since 2026-10-28 16:07:11 UTC: weed v1.2.0, /etc/weed/weed.toml
              (sha256 b78bbdeed036); restart pending: the configuration file has
              changed: server.port"

/status

On server.metrics_address, /status tells all of it as JSON: the build, the pid, since when weed runs, the configuration (file, SHA-256 and every option), how the last reload went, whether a restart is pending and why, the workers, the banned users and the requests in progress. Monitoring shows a full answer.

$ curl -s localhost:9100/status | jq .restart_pending
{
  "config": "the configuration file has changed: server.port"
}

The same is in the metrics weed_build_info, weed_config_info, weed_restart_pending and process_start_time_seconds (see Metrics). For example, alert when a restart has been pending for a day, and when servers that should run the same build do not:

weed_restart_pending == 1                       for: 1d
count(count by (build) (weed_build_info)) > 1

weed check

weed check does what starting does, without serving: it reads the configuration and every file it names (credential files, the certificate and its key, CAs, CRLs, token issuers, the bans), contacts the OIDC provider, and starts a worker as nobody. It prints the warnings that weed would log, and the SHA-256 of the file. If weed would not start, it says why and exits with 1.

# weed check -config /etc/weed/weed.toml
/etc/weed/weed.toml: weed would start with it (sha256 6794c30b95c0972e5a032630bb90ccdf474c3df01a9dd983f88c9fdc5baf417e)

It does not try to listen on the configured addresses, which are in use while weed runs, nor set cgroups up. Run it before every restart (see Upgrading).
